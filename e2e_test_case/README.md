# e2e 평가셋

## 핵심 요약

기존 평가셋은 agent 결과를 미리 예측해 정답으로 못박고 답변을 문자열로 채점해서, 실패가 나와도
agent 탓인지 채점 탓인지 가를 수 없었습니다. 이 문제를 해결하기 위해 평가를 **결정론 · 궤적 ·
답변** 세 갈래로 나누고, 문제를 **core(기본) 70 · edge(까다로운 입력) 30** 으로 나눠 평가합니다.

```
결정론       코드       무엇을 했나 — route · tool · 인자
궤적 judge   LLM       어떤 순서로 했나 — 라벨을 읽지 않는 독립 판정
답변 judge   LLM       최종 답이 좋은가 — 기대동작 체크리스트 + 원자료 대조
```

세 갈래 구분은 LangSmith 의 agent 평가 분류(individual steps · trajectory · final response)를 따랐고,
궤적 judge 프롬프트는 LangChain `agentevals` 의 표준 프롬프트를, 답변 judge 의 rubric 채점과 judge
점검 방식은 Anthropic 평가 문서(Develop tests)를 참고했습니다. 결정론 채점 규칙과 라벨 오류를 막는
장치는 이 agent 에 맞춰 직접 설계했습니다.

## 핵심 결과

문제 100개(core 70 · edge 30)를 실행 20260922-144602 에서 한 번 돌렸습니다.

```
            결정론     궤적      답변      최종
전체        97/100    88/100    68/100    68/100
  core      69/70     61/70     47/70     47/70
  edge      28/30     27/30     21/30     21/30

영역        환율 8/8 · 범위 밖 5/5 · 규정 20/26 · 상품 25/50
```

**tool 선택은 거의 맞지만, 답변 생성에서 떨어집니다.** 결정론은 통과했는데 답변이 실패한 케이스가
29건입니다. 가장 약한 곳은 상품추천(25/50)이고, 원인 대부분은 금리 숫자 불일치입니다. 같은 은행
상품이 여러 개일 때 숫자 교정 가드레일이 다른 상품의 값으로 덮어쓰는 것으로 보입니다(가설).

결정론 FAIL + 궤적 PASS 는 0건입니다. 라벨이 틀렸다는 신호는 나오지 않았습니다.

케이스별 결과 카드와 상세 집계는 [runs/20260922-144602/README.md](runs/20260922-144602/README.md) 에 있습니다.

## 평가체계 구조

결정론은 코드로, 비결정론은 LLM-as-judge 기반으로 채점합니다. 세부적으로는 다음과 같이 합니다.

### 왜 이렇게 했나

**FAIL 이 나왔을 때 그게 agent 탓인지 채점 탓인지 가를 수 있게 만들었습니다.** 기존 평가셋은
실패 8건 중 6건이 agent 가 아니라 테스트셋 쪽 오류였고, 이를 하나씩 파고들어서야 알 수 있었습니다.

- **정답이 하나인 것은 코드로, 여러 개인 것은 LLM 으로 채점합니다.** 답변을 문자열로 채점하면
  표현만 다른 정상 답변이 실패로 찍힙니다
- **궤적 judge 는 라벨을 읽지 않습니다.** 라벨과 독립된 두 번째 의견이 생기고, 결정론과 엇갈리면
  라벨을 의심합니다
- **문제를 agent 를 돌리기 전에 씁니다.** 라벨이 agent 결과를 따라가지 못하게 합니다
- **judge 는 agent 와 다른 계열 모델로, 배치마다 새로 띄웁니다.** 자기 출력을 후하게 보거나 앞
  케이스에 끌려가지 않게 합니다

### 결정론

agent 가 **무엇을 했는지**를 코드로 봅니다. 답변 문장은 보지 않습니다.

| 칸 | 보는 것 |
| --- | --- |
| 기대route | 라우터가 맞는 경로로 보냈는가 |
| 필수도구 · 금지도구 · 도구없음 | 불러야 할 tool 을 불렀는가, 부르면 안 될 tool 을 불렀는가 |
| 기대인자 | 사용자가 말한 조건을 **첫 호출**에 넣었는가 (은행명은 부분 일치) |
| 금지인자 | 사용자가 말하지 않은 조건을 지어넣었는가 |

**참고한 것**
- LangSmith agent 평가의 *individual steps* 분류 — 단계마다 도구를 맞게 골랐는지 봅니다
- Anthropic 평가 문서(Develop tests) — 규칙으로 판정할 수 있는 것은 코드 채점이 가장 빠르고
  신뢰할 만합니다. 그래서 LangSmith 예시처럼 LLM 으로 재지 않고 코드로 쟀습니다
- 칸 구성과 채점 규칙(첫 호출만 보기, 부분 일치)은 이 agent 에 맞춰 직접 정했습니다

### 궤적 judge

agent 가 **어떤 순서로 했는지**를 LLM 이 봅니다. 라우팅 · Tier0 재작성 · tool 호출과 재시도 · 가드레일
기록만 보고, 문제 카드의 라벨은 읽지 않습니다. 그래서 결정론은 FAIL 인데 궤적은 PASS 라면 라벨이
틀렸을 수 있다는 신호가 됩니다.

**참고한 것**
- LangSmith agent 평가의 *trajectory* 분류
- LangChain `agentevals` 의 `TRAJECTORY_ACCURACY_PROMPT` (참조 궤적 없는 판) 를 그대로 쓰고 한 줄만
  더했습니다 — "API 실패나 빈 결과 뒤의 재시도 · 재해석 1회는 비효율이 아니다". 표준 기준대로라면
  Tier1 · Tier2 재시도가 감점되기 때문입니다

### 답변 judge

최종 답변이 **좋은지**를 LLM 이 봅니다. 질문 · 기대동작 · 원자료(tool 결과와 RAG 문서 전문) · 답변만
주고, tool 이름과 결정론 결과는 주지 않습니다.

```
기대동작을 전부 충족하는가               정답 문장이 아니라 체크리스트
"없음" 과 "못 봄" 을 구분하는가
── 하나라도 어기면 실패 ──
원금보장 · 확정수익 같은 단정 표현
원자료에 없는 숫자 (금리 · 한도 · 날짜)
바꾼 조건을 숨김 (18개월을 물었는데 12개월을 말없이 제시)
문서가 뒷받침하지 않는 규정
```

**참고한 것**
- LangSmith agent 평가의 *final response* 분류
- Anthropic 평가 문서(Develop tests) — 정답 대신 rubric 으로 채점하기, 판정 근거와 결과를 태그로
  나눠 받기(`<evidence>` · `<result>`), 실제 채점 전에 judge 가 제대로 도는지 점검하기
  (명백히 좋은 답 5 · 나쁜 답 5 → 10/10)
- 즉시 실패 규칙 4개는 은행 상담 보조라는 도메인에 맞춰 직접 정했습니다

judge 는 Claude(Opus) 서브에이전트로 돌렸습니다. agent(OpenAI)와 다른 계열이라 자기 출력을 후하게
채점하지 않습니다. 배치마다 새로 띄우고 배치 파일 하나만 읽게 했습니다.

## 폴더 구조

```
e2e_test_case/
├─ README.md
├─ CASES.md                     문제 카드 100장을 표 한 장으로 정리 (overview.py 가 생성)
├─ core/                        문제 카드 70장 — C001.yaml … C070.yaml
├─ edge/                        문제 카드 30장 — E001.yaml … E030.yaml
├─ judge_sanity.yaml            judge 점검용 합성 10건 (좋은 답 5 · 나쁜 답 5)
├─ prompts/
│   ├─ trajectory_judge.txt     궤적 judge
│   └─ answer_judge.txt         답변 judge
├─ harness/
│   ├─ case.py                  문제 카드 스키마 · 결정론 채점
│   ├─ run.py                   agent 실행 → 궤적 기록 → 결정론 채점 → judge 배치 생성
│   ├─ batches.py               judge 배치 · sanity 배치 · 재판정 배치 생성
│   ├─ cards.py                 세 판정을 결과 카드와 요약표로 통합
│   └─ overview.py              CASES.md 생성
└─ runs/
    ├─ sanity/                  judge 점검 배치 · 정답지 · 판정 결과
    └─ 20260922-144602/         1차 실행
        ├─ README.md            요약표 · 실패 케이스 목록
        ├─ core/ · edge/        결과 카드 — 케이스 하나에 결정론 · 궤적 · 답변 판정
        ├─ traces/              케이스별 실행 기록 (route · tool 호출 · 가드레일 · 답변 · 원자료)
        ├─ deterministic.json   결정론 결과
        └─ judge/               배치 · 판정 결과 · 재판정 기록
```

**문제 카드와 결과 카드를 나눕니다.** 문제 카드(`core/` · `edge/`)는 agent 를 돌리기 전에 쓰고 고치지
않습니다. 결과는 돌릴 때마다 `runs/<실행 시각>/` 아래에 새로 쌓이고, 문제 카드와 같은 모양
(`core/C017.yaml` → `runs/…/core/C017.md`)으로 놓입니다.

```
실행 순서
  python e2e_test_case/harness/batches.py           judge 점검 배치
  python e2e_test_case/harness/run.py               100문제 실행 · 결정론 · judge 배치
  (judge 판정 → runs/<시각>/judge/*.result.md)
  python e2e_test_case/harness/cards.py runs/<시각>  결과 카드 · 요약표
```
